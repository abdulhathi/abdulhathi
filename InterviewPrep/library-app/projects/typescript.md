## What you will build

A library, not an app: `fetchwise` wraps `fetch` so that every call is typed end to end. You describe an endpoint once (method, path with parameters, request and response schemas in zod), and get a function whose arguments and return type are inferred. It validates responses at runtime, retries safe requests with exponential backoff and jitter, honours `Retry-After`, supports timeouts and `AbortSignal`, and returns a `Result` type instead of throwing, so callers must handle errors.

Publishing to npm is the point: a recruiter can `npm install` it, read the types in their editor, and see the CI, tests and changelog. Before you start, check the name is free on npm (use a scoped name such as `@yourname/fetchwise` if not).

## What it proves

- Advanced TypeScript: generics, conditional and template literal types (path parameters from `"/users/:id"`), inference from zod schemas, discriminated unions for results
- Runtime validation at boundaries with zod
- Async JavaScript done right: retries with backoff and jitter, timeouts with `AbortSignal.any`, cancellation
- Library engineering: ESM + CJS builds, type declarations, semantic versioning, changesets, npm provenance
- Testing with Vitest and MSW, type tests
- Keywords: TypeScript, zod, npm package, Vitest, MSW, CI/CD, semantic versioning, API client

## Architecture

```text
 defineEndpoint({ method, path: "/users/:id", params, query, body, response })   ← zod schemas
          │  types inferred:  (args: { params: { id: string } }) => Promise<Result<User, ApiError>>
          ▼
 createClient({ baseUrl, headers, retry, timeoutMs, fetch })
          │
          ▼  per call:  build URL → serialise → fetch with AbortSignal.any([caller, timeout])
          │             → retry on 429/503 (idempotent methods only, Retry-After, jittered backoff)
          │             → parse JSON → validate with the response schema
          ▼
   Result<T, ApiError>   where ApiError = { kind: "network" | "timeout" | "http" | "validation", … }
```

## Milestones

### Milestone 1: the typed endpoint definition

Goal: inference works before any network code exists.

- `defineEndpoint` captures method, path and zod schemas; a `PathParams<"/users/:id/posts/:postId">` type extracts `{ id: string; postId: string }`.
- Type tests with `expectTypeOf` (Vitest) so the types are tested like code.

Done when: a wrong parameter name or a missing body is a compile error, proved by type tests.

### Milestone 2: the client and the Result type

- `createClient` returns a function per endpoint; build URLs safely (encode parameters), serialise JSON bodies, parse responses.
- `Result<T, E>` as a discriminated union (`{ ok: true; value }` / `{ ok: false; error }`) with helpers.
- Validate responses; a schema mismatch is a `validation` error that includes the zod issues.

Done when: tests against MSW cover success, 4xx, 5xx, invalid JSON and schema mismatch.

### Milestone 3: timeouts, cancellation and retries

- Combine the caller's signal with a timeout using `AbortSignal.any`.
- Retry only idempotent methods (or POSTs with an idempotency key) on network errors, 429 and 503; exponential backoff with full jitter; respect `Retry-After`; cap attempts and total time.
- An injectable clock and random source so tests are deterministic.

Done when: tests with fake timers prove the retry schedule, that cancellation stops retries immediately, and that a POST without an idempotency key is never retried.

### Milestone 4: build, docs and publish

- Build ESM and CJS with type declarations (tsup or tsc); check the package with `publint` and `@arethetypeswrong/cli`.
- A README with a 30-second example, an API reference generated by TypeDoc and published to GitHub Pages.
- Changesets for versioning; publish `0.1.0` from GitHub Actions with npm provenance.

Done when: `npm install @yourname/fetchwise` works in a fresh project and the types show up in the editor.

### Milestone 5: an example app

- An `examples/` folder with a tiny React or Node script that uses the client against a public API.

Done when: the example runs with one command and appears in the README.

## Tests and CI

- **Unit and behaviour:** MSW handlers for every error path; fake timers for retries and timeouts.
- **Type tests:** `expectTypeOf` for inference, and `@ts-expect-error` for calls that must not compile.
- **Package checks:** `publint` and `attw` on every PR so a broken export never ships.

```yaml
# .github/workflows/ci.yml (outline)
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { node: [20, 22, 24] }
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: "${{ matrix.node }}", cache: npm }
      - run: npm ci
      - run: npx tsc --noEmit
      - run: npx vitest run --typecheck
      - run: npm run build && npx publint && npx attw --pack
```

## Talking about it in an interview

**60-second walkthrough:** "fetchwise is a small typed HTTP client I published to npm. You describe an endpoint once with zod schemas and the path, and the types for parameters, body and response are inferred, including path parameters parsed from the URL template with template literal types. At runtime it validates responses, so a backend change shows up as a typed validation error, not a crash three components later. It retries only safe requests, with jittered backoff and Retry-After, and timeouts compose with the caller's AbortSignal. Errors come back as a discriminated union, so the compiler makes callers handle them."

- **Why validate responses if you have types?** Types disappear at runtime; the server can change. Validation at the boundary turns a silent bad value into an explicit error.
- **How do you avoid retrying a payment twice?** Only idempotent methods are retried, and POSTs only with an idempotency key the server deduplicates on.
- **How do you test types?** Type tests with `expectTypeOf` run in CI, and `@ts-expect-error` lines fail the build if an invalid call starts compiling.
