01 · Foundations

What you will build

ShopFlow takes orders over HTTP and hands the work to independent services through RabbitMQ.

The order API never calls the fulfilment or email services directly. It publishes an order created event and returns. The fulfilment service packs the order and publishes order shipped. The notification service emails the customer for both events. If a service is slow, restarting, or scaled to five copies, the API does not notice. That decoupling is the reason message brokers exist.

02 · Foundations

The vocabulary

Ten words explain almost everything RabbitMQ does. Learn them once and every later chapter reads easily.

The one idea to keep

Producers never publish straight into a queue. They publish to an exchange with a routing key. The exchange looks at its type and its bindings and decides which queues get a copy. Even sendToQueue() goes through an exchange: the nameless default exchange.

TermWhat it is
BrokerThe RabbitMQ server. It stores and routes messages.
ConnectionOne TCP connection from your process to the broker. Expensive to open, so keep one per process.
ChannelA lightweight virtual connection inside a connection. Almost every operation happens on a channel.
ProducerCode that publishes messages.
ExchangeReceives messages and routes them to queues. Its type (direct, fanout, topic, headers) sets the routing rule.
Routing keyA string the producer attaches to each message, such as order.created.eu.
BindingA rule that links an exchange to a queue, optionally with a key or pattern.
QueueAn ordered buffer that holds messages until a consumer takes them.
ConsumerCode that subscribes to a queue and processes its messages.
AckThe consumer telling the broker "done, delete it". Without an ack, the broker keeps the message and can redeliver it.
Virtual hostA namespace for exchanges, queues and permissions. We use the default /.

What a message carries

RabbitMQ treats the body as bytes. Everything else travels as properties or delivery information.

PartExamplesSet by
BodyJSON order, bytes of any formatProducer
PropertiescontentType, persistent, messageId, correlationId, replyTo, expiration, headersProducer
Delivery infoexchange, routingKey, redelivered, deliveryTagBroker, on delivery
Checkpoint

A producer calls channel.publish('shop', 'order.created.eu', body), but no queue is bound to shop. Where does the message go?

Show answer

Nowhere. The exchange finds no matching binding and drops the message. Chapter 10 shows how to get it back with the mandatory flag.

Set up the project

A TypeScript project that runs any file with one command, plus two helpers every chapter reuses.

amqplib is the Node client for RabbitMQ. Version 2 ships its own TypeScript types and can reconnect by itself (chapter 14). tsx runs TypeScript files directly, so there is no build step: every script runs with npx tsx path/to/file.ts.

Add a tsconfig.json so your editor and npx tsc can type-check the project.

Where everything will live

The connection helper

Every script opens one connection and one channel the same way.

Connections and channels

A connection is a TCP socket with a handshake, authentication and heartbeats. A channel is a cheap virtual connection multiplexed inside it. Open one connection per process and channels as needed. Opening a connection for every message is the most common RabbitMQ performance mistake.

05 · Core patterns · src/01-hello

Hello queue

Send one message to a queue and receive it. You will meet queue declaration, the default exchange and auto-ack.

Run it

What just happened

  • assertQueue creates the queue if it is missing and does nothing if it already exists with the same settings. Both sides call it, so start order does not matter.
  • sendToQueue publishes to the default exchange, which has an implicit binding to every queue by name. The routing key hello lands in queue hello.
  • noAck: true means the broker deletes the message the moment it sends it. Simple, but a crash mid-processing loses the message. Chapter 06 fixes this.
  • durable: false means the queue disappears if the broker restarts. Fine for a hello world, wrong for orders.
Try this
  1. Stop the receiver. Run send.ts three times.
  2. Open Queues and Streams: hello shows Ready 3. The queue buffers messages until someone wants them.
  3. Start the receiver again. All three arrive at once.
Checkpoint

Why does the receiver declare the queue even though the sender already does?

Show answer

Because you cannot know which process starts first. If the receiver tried to consume from a queue that does not exist, the broker would close the channel with a NOT_FOUND error. Declaring is idempotent, so both sides do it safely.

06 · Core patterns · src/02-work-queues

Work queues and acks

Spread slow jobs across several workers without losing any, even when a worker crashes.

Packing an order takes time: one second per line item in our simulation. One worker cannot keep up, so you run several. They compete for messages on the same queue, and each order goes to exactly one of them.

Run it

The four ideas in this chapter

Competing consumers

Several consumers on one queue share the work. Add a worker to go faster; remove one and the rest carry on. This is how you scale a consumer horizontally.

Manual acknowledgements

With noAck: false, the broker keeps each message until the worker calls channel.ack(msg). If the worker's channel or connection closes first, the broker puts the message back in the queue and delivers it to another worker, with msg.fields.redelivered set to true. Always ack after the work is done.

Prefetch

Without a limit, the broker pushes messages to consumers as fast as it can, round-robin, regardless of how busy they are. channel.prefetch(1) says "at most one unacked message for me", so a worker stuck on a 4-second order does not hoard the queue. Higher values (10 to 50) give more throughput for fast jobs.

Durability takes two settings

A durable queue survives a broker restart. A persistent message is written to disk. You need both: a persistent message in a non-durable queue is lost with the queue, and a durable queue full of transient messages comes back empty.

Try this
  1. Crash a worker. Run only alice, queue 6 orders, and press Ctrl+C while she is packing. Start bob: he receives the order alice never acked. Log msg.fields.redelivered to see true.
  2. Forget the ack. Comment out channel.ack(msg). In the UI, Unacked climbs and never falls. Stop the worker and watch them move back to Ready.
  3. Survive a restart. Stop all workers, queue 6 orders, then run docker compose restart rabbitmq. The orders are still there.
Gotcha

You cannot change durable (or any other setting) on a queue that already exists. The broker closes the channel with PRECONDITION_FAILED - inequivalent arg 'durable'. Delete the queue in the UI first, or use a new name.

Checkpoint

Two workers with prefetch 1. The first order takes 10 seconds and the next five take 1 second each. Who packs what?

Show answer

The worker on the long order receives nothing else until it acks. The other worker packs all five short orders in about 5 seconds. Without prefetch, the broker would have pushed three orders to each worker up front, and two short orders would wait behind the long one.

07 · Core patterns · src/03-fanout

Fanout: publish/subscribe

Send every order to several services at once, without the publisher knowing who they are.

A work queue gives each message to one consumer. Now you want the opposite: the email service, the analytics service and a live dashboard should all see every order. Each gets its own queue, and a fanout exchange copies every message to every bound queue.

Run it

Two kinds of subscriber queue

  • Named and durable (orders.placed.email): owned by a service. Messages wait there while the service is down, so it never misses an order.
  • Server-named and exclusive (amq.gen-…): the broker picks the name and deletes the queue when the connection closes. Right for a live view that only cares about now.

The binding (bindQueue) is what connects a queue to an exchange. A fanout exchange ignores routing keys, which is why every call passes an empty string.

Try this
  1. Stop the email subscriber and place 3 orders. In the UI, orders.placed.email shows Ready 3. Restart it and the backlog arrives.
  2. Stop the live feed. Its amq.gen-… queue vanishes from the Queues tab. Orders placed now are never seen by it.
  3. Open Exchanges → orders.placed and look at the bindings list.
Checkpoint

Next month you add a fraud-check service. What changes in place-order.ts?

Show answer

Nothing. The fraud service declares its own queue and binds it to orders.placed. Producers and consumers only share the exchange name, which is the decoupling you are after.

08 · Core patterns · src/04-direct

Direct: routing by key

Send each order only to the warehouse that serves its region.

A direct exchange compares the message's routing key with each binding key and delivers on an exact match. The order's region becomes the routing key. One queue can have several bindings, so a single warehouse can serve two regions.

Run it

  • Exact match only. us matches us, never US or us-west.
  • The same key on two queues gives both a copy, so a direct exchange can fan out per key.
  • No match means the message is dropped, silently. The producer is not told.
Try this
  1. Start a third warehouse with warehouse.ts us eu. Route 6 orders: eu orders now reach two queues.
  2. Stop all warehouses. In the UI, delete the queues warehouse.eu-apac and warehouse.us-eu. Route 6 orders. Only warehouse.us grows; every eu and apac order is gone. Remember this for chapter 10.

09 · Core patterns · src/05-topic

Topic: routing by pattern

Let each consumer choose the events it wants with wildcard patterns.

Order events now carry structured keys: order.<event>.<region>, for example order.cancelled.eu. A topic exchange splits keys on dots and matches them against binding patterns with two wildcards:

  • * matches exactly one word.
  • # matches zero or more words.

Quote the patterns in your shell. Otherwise zsh or bash may try to expand * as a file glob.

Gotcha

Bindings belong to the broker, not to your process. They stay after the listener stops, and running listener.ts audit 'order.paid.*' later adds a binding to events.audit instead of replacing order.#. Remove old ones in Exchanges → order.events → Bindings → Unbind, or call channel.unbindQueue().

Checkpoint

What does a topic binding of # alone behave like? And a pattern with no wildcards?

Show answer

# matches every key, so the queue behaves like it is bound to a fanout exchange. A pattern with no wildcards matches only that exact key, like a direct binding. Topic exchanges cover both cases, which is why many systems use them by default.

10 · Production concerns · src/06-reliability

Reliable delivery

Close every gap where a message can be lost between producer, broker and consumer.

A message passes through three handoffs. Each one needs its own safeguard.

HandoffWhat can go wrongSafeguard
Producer → brokerNetwork drops, broker crashes before storing, no queue matchesPublisher confirms, mandatory: true with a return handler
Inside the brokerBroker restarts or its disk failsDurable queue + persistent message; quorum queues replicate across nodes (chapter 11)
Broker → consumerConsumer crashes mid-processingManual ack after the work (chapter 06)

Publisher confirms and returns

On a confirm channel the broker answers every publish with an ack (stored safely) or a nack (could not store it). With mandatory: true, a message that matches no queue is handed back through a return event instead of being dropped.

A returned message is still confirmed, because the broker did handle it. Treat the return as the signal that something is misconfigured. An alternative is an alternate exchange (assertExchange(name, type, { alternateExchange: 'unrouted' })), which routes unmatched messages to a catch-all queue instead.

Confirms are asynchronous. For throughput, publish a batch and call waitForConfirms() once, rather than waiting after every single message.

At-least-once means duplicates

Put the safeguards together and RabbitMQ gives you at-least-once delivery: nothing is lost, but a message can arrive twice. A consumer that finishes the work and crashes before its ack will see the message again. A producer that times out waiting for a confirm will publish again. Exactly-once delivery does not exist end to end, so make consumers idempotent: give each message a messageId and skip ids you have already processed. ShopFlow's notification service does this in chapter 14.

GuaranteeSettingsTrade-off
At-most-onceAuto-ack, no confirms, transient messagesFastest; loses messages on any failure
At-least-onceManual acks, confirms, durable + persistentNo loss; consumers must handle duplicates
Checkpoint

Your API publishes an order, gets no confirm within 5 seconds, and publishes it again. Both copies reach the queue. Which component should deal with that, and how?

Show answer

The consumer. Both copies carry the same messageId (the order id), so the consumer records processed ids in a store with a unique key and acks duplicates without doing the work again.

11 · Production concerns · concept only

Queue types

Choose between classic, quorum and stream queues, and know why quorum is the default for data you cannot lose.

So far every queue has been a classic queue, the default type. RabbitMQ 4 offers two more, chosen with the x-queue-type argument when you declare the queue. Classic mirrored queues were removed in RabbitMQ 4.0; quorum queues replace them.

ClassicQuorumStream
Declare with(default)'x-queue-type': 'quorum''x-queue-type': 'stream'
ReplicationNone, lives on one nodeRaft consensus across 3, 5 or 7 nodesReplicated append-only log
After consumingMessage deleted on ackMessage deleted on ackKept; consumers read from an offset and can replay
Poison messagesNo built-in limitx-delivery-limit (default 20 in 4.x)Not applicable
Exclusive, non-durableSupportedNot supported: always durableNot supported
Use it forTemporary, exclusive and reply queuesOrders, payments, anything you cannot loseEvent history, many consumers reading the same data, replay
Rule of thumb

Quorum for anything important, classic for temporary and exclusive queues, stream when consumers need history. On a single node, as in this tutorial, a quorum queue cannot replicate, but you still get the delivery limit, and moving to a 3-node cluster later needs no code change.

Gotcha

A queue's type cannot change after it is created. Declaring an existing classic queue as quorum fails with PRECONDITION_FAILED - inequivalent arg 'x-queue-type'. Delete the queue and declare it again, or migrate to a new name.

12 · Production concerns · src/07-dead-letters

Dead letters and retries

Retry failures that might succeed later, park failures that never will, and stop poison messages from looping forever.

Charging a card can fail in two very different ways. A declined card will never succeed, so retrying is pointless. A gateway timeout might succeed in a few seconds. The payment worker treats them differently, using three queues:

  • payments: the main work queue. Rejected messages are dead-lettered to payments.dlx.
  • payments.retry: a waiting room with a 5-second TTL and no consumer. Expired messages dead-letter straight back into payments.
  • payments.dead: the parking lot, where a human looks at what failed.

Run it

How dead-lettering works

A queue with a deadLetterExchange republishes a message to that exchange, instead of dropping it, when one of these happens:

x-death reasonCauseSeen in this chapter
rejectedConsumer called nack or reject with requeue: falseDeclined card, retries used up
expiredMessage TTL or per-message expiration ran outEvery pass through payments.retry
delivery_limitA quorum queue redelivered it more than x-delivery-limit timesThe poison message experiment below
maxlenThe queue hit its length limit with overflow set to drop the oldestNot used here

The broker adds an x-death header recording each death: reason, queue and count. ord_down shows expired … x1 rather than x3 because each retry publishes a fresh copy with a new retry-count header, so the broker's history restarts each time. Your own header carries the real attempt count.

inspect-dead.ts reads with channel.get and never acks. Closing the channel returns every unacked message to the queue, so the parking lot stays intact no matter how often you inspect it.

Try this: a poison message
  1. In payment-worker.ts, change the last branch to channel.nack(msg, false, true), which requeues instead of rejecting.
  2. Publish the payments again. ord_declined is now redelivered immediately, over and over. Log msg.properties.headers?.['x-delivery-count'] to watch it climb.
  3. After the 6th delivery (1 + 5 redeliveries), the quorum queue gives up and dead-letters it. inspect-dead.ts shows delivery_limit in payments x1.
  4. Change the line back. Purge payments.dead from its page in the UI.

This is why immediate requeue is dangerous: a message that always fails becomes a hot loop that burns CPU and blocks the queue. The delivery limit is the safety net; the delayed retry queue is the proper fix.

Checkpoint

Why does the worker publish a copy to payments.retry and ack the original, instead of nacking it?

Show answer

A nack with requeue retries immediately, with no delay, which gives the gateway no time to recover. A nack without requeue sends the message to the parking lot. Publishing a copy with a higher retry-count to a TTL queue gives a delayed retry and lets the worker count attempts.

13 · Production concerns · src/08-rpc

Request/reply (RPC)

Ask a service a question over RabbitMQ and wait for the answer.

Checkout needs a shipping quote before the customer pays. The quote service sits behind a queue, so you can run several copies of it. The client sends a request with two properties:

  • replyTo: the queue the answer should go to, here the client's private exclusive queue.
  • correlationId: a unique id the server copies into the reply, so the client can match answers to questions.

Run it

First run the client alone to see the timeout, then start the server and run the client again.

  • Always time out. If no server is running, the request waits in the queue. The client gives up after 3 seconds, and expiration makes the broker drop the stale request so no server wastes time on it later.
  • Requests run in parallel. Three quotes go out at once; the correlation ids sort out the replies.
  • Direct reply-to. RabbitMQ also offers the pseudo-queue amq.rabbitmq.reply-to, which skips declaring a reply queue. Try it as an extension.
When to use it

RPC over a broker adds latency and couples the caller to an answer. Use it when you want load-balanced workers behind a request, such as quotes, pricing or image processing. For workflows like "order placed → pack → ship", publish events and let services react, as ShopFlow does.

14 · Finish · src/09-shopflow

Assemble ShopFlow

Combine the patterns into one small application that survives broker restarts.

Topology as code

Every exchange, queue and binding is declared in one file. Each service calls it on startup, so the broker always matches the code, whichever service starts first.

A service runner that reconnects

Until now, a broker restart killed every script. amqplib 2 can reconnect for you: pass recovery options and a setup function. After every successful connect, including reconnects, setup runs again and re-creates the channel, the queues and the consumer.

The order API

A plain Node HTTP server. It answers 202 Accepted only after the broker confirms the order, and 503 if it is offline, so a client never believes an order was taken when it was not.

The two consumers

Fulfilment packs orders and publishes order.shipped.<region> back to the same exchange, so it is a consumer and a producer. Notifications remembers what it already sent, which makes it idempotent.

Run it

The resilience drill
  1. With all three services running, stop the broker: docker compose stop rabbitmq.
  2. Every service logs Connection lost and starts reconnecting with growing delays. A curl now returns Order not accepted, try again (HTTP 503).
  3. Start it again: docker compose start rabbitmq. Within a few seconds each service logs Connected, and new orders flow end to end.
  4. Start a second fulfilment-service in another terminal and post five orders. Two competing consumers now share the packing.

What ShopFlow demonstrates

  • Topic routing so new consumers can subscribe without touching producers.
  • Publisher confirms at the edge: the API never acknowledges an order the broker does not have.
  • Quorum queues with a delivery limit and a dead-letter exchange for failure handling.
  • Automatic recovery, with topology re-declared after every reconnect.
  • Idempotent consumers, because at-least-once delivery means duplicates.
  • Graceful shutdown: on Ctrl+C the connection closes and unacked messages return to their queues.
